# CZSC 0.9 Python 实现与本项目结合方案

## 结论

CZSC 0.9 对本项目有实质帮助，但正确的结合方式不是把 `czsc==0.9.68`
直接装进生产环境，也不是替换现有 `ChanEngine`。建议保持本项目的
`CanonicalBar -> ChanEngine -> 冻结快照 -> React/ECharts` 权威链路，选择性吸收
CZSC 0.9 的四项能力：

1. 增量处理末端 K 线、分型和笔的状态模型。
2. `RawBar -> NewBar -> FX -> BI -> ZS` 的结构分层和来源追踪。
3. `BarGenerator -> CzscSignals` 的多周期编排与版本化信号注册。
4. 分型、笔、MACD、买卖点的 ECharts 图层设计和官方回归样本。

其中，包含、分型、笔算法只能作为差分基准和改造参考；多周期、信号和可视化只能
复用架构，不能直接复用数据契约。CZSC 0.9 没有线段核心模型，也没有现成的中枢
矩形绘制能力，不能补齐本项目后续全部缠论信号栈。

## 研究基线

### 版本

官方 0.9 系列最后一个标签是 `0.9.68`，对应提交
[`3dfa3db215b9c01ae53251743704eef25814512c`][czsc-tree]，提交时间为
2025-06-12。本文所有外部源码结论都固定到该提交，不引用持续变化的 `master`。

### “纯 Python”的准确边界

`0.9.68` 的缠论分析主链确实由 Python 实现：包含处理、分型、笔、中枢对象、
多周期编排和信号函数都在 Python 文件中。但整个发布包并不是纯 Python：

- `requirements.txt` 已把 `rs_czsc>=0.1.6` 列为依赖。[依赖清单][requirements]
- 顶层 `czsc/__init__.py` 会直接从 `rs_czsc` 导入回测与绩效函数。
  [顶层导入][init]
- 整包还带入 pandas、NumPy、SciPy、TA-Lib、Streamlit、pyecharts、
  lightweight-charts 等大量依赖。[依赖清单][requirements]

因此可以把 0.9 的 Python 源码作为参考实现，不能把安装整包理解为低成本的
“纯 Python 接入”。如果直接复制源码，需要按官方 Apache-2.0 许可证保留相应
版权和许可声明。[许可证][license]

## 本项目当前基线

当前生产链路已经形成完整边界：

```text
Tushare 前复权行情
  -> CanonicalBar
  -> ChanEngine
  -> market_snapshot / chan_analysis
  -> React API 适配
  -> ECharts K 线、笔、中枢、成交量
```

关键事实如下：

- `apps/api/app/domain/chan_engine.py` 使用 `Decimal`，并保存
  `occurred_at`、`known_at`、`stable_through`、`payload_hash`。
- `ChanEngine` 已实现包含处理、严格分型、笔和顺序笔中枢。
- `MarketAnalysisService` 固化前复权行情、快照 ID 和引擎版本。
- `apps/web/src/api.ts` 把结构 K 线索引转换成图表日期。
- `ChanChart` 和 `buildChanChartOption` 已用原生 ECharts 绘制 K 线、确认笔、
  形成中笔、笔中枢和成交量。
- 线段、线段中枢、走势类型、MACD 背驰和一二三类买卖点目前仍是设计，尚未进入
  生产代码。

这意味着 CZSC 只能进入算法内部或旁路研究层，不能越过现有快照、时间可用性、
报告引用和前端契约。

## CZSC 0.9 的实现方式

### 1. 包含、分型和笔

CZSC 用分层对象保存结构来源：

| CZSC 对象 | 作用 | 与本项目对应关系 |
| --- | --- | --- |
| `RawBar` | 原始 OHLCV、递增 ID、可变缓存 | `CanonicalBar`，但缺少时间可用性字段 |
| `NewBar` | 去包含后的 K 线，`elements` 保存原始 K 线 | 当前归一化 K 线，尚未保存来源索引 |
| `FX` | 三根 `NewBar` 构成的顶底分型 | `snapshot.fractals` |
| `BI` | 起止分型、内部 K 线、内部次级分型及力度 | `snapshot.strokes` |
| `ZS` | 调用方传入一组笔后计算中枢属性 | `snapshot.centers`，但分组语义不同 |

对象字段和派生属性见 [`objects.py`][objects]。

`remove_include` 使用前两根无包含 K 线判断方向，再合并第三根原始 K 线；上涨合并
取更高的高点和低点，下跌合并取更低的高点和低点，同时累计成交量、成交额并保留
原始元素。[包含处理源码][analyze-include]

`check_fx` 使用严格三 K 线条件识别顶底分型。`check_bi` 先找交替分型，再要求
起止分型不包含、间距达到 `min_bi_len`，最后生成带内部 K 线和分型的 `BI`。
[分型与笔源码][analyze-bi]

`CZSC.update` 只处理末端状态：相同时间 K 线会覆盖上一根并重算尾部；新 K 线先去
包含，再尝试生成新笔；若最新未完成结构破坏上一笔，会弹出上一笔并把其尾部 K 线
放回未完成区重新计算。[增量更新源码][analyze-update]

这比本项目当前 `replay -> 逐根 ingest -> 每根全量 _reduce` 更高效，但更新语义并不
兼容：本项目对相同证券、相同时间、不同内容直接报错，以保证冻结报告可以复现。

### 2. 中枢

0.9 的 `CZSC` 分析器只维护 `bi_list`，不会维护权威 `zs_list`。`ZS` 是一个辅助
对象，调用方把任意一组 `BI` 传进去后，才计算：

- `zg`：前三笔高点的最小值。
- `zd`：前三笔低点的最大值。
- `gg` / `dd`：全部笔的最高点和最低点。
- `zz`：中枢中轴。
- `is_valid`：上下沿相交，且每一笔都与中枢区间相交。

这些属性见 [`ZS` 对象源码][objects-zs]。`get_zs_seq` 只是根据信号计算需要，把
连续笔按当前中枢上下沿分组；它不属于 `CZSC` 核心输出，也不等同于本项目当前
“找到三笔重叠后顺序延伸，离开后再找下一中枢”的规则。
[中枢序列辅助函数][get-zs-seq]

因此可复用的是 `zg`、`zd`、`gg`、`dd`、`zz` 和有效性检查，不应直接用
`get_zs_seq` 替换本项目 `build_centers`。

### 3. 线段

结论明确：CZSC 0.9.68 没有线段核心模型。

- `objects.py` 没有 `XD`、`Segment` 或对应结构对象。[对象定义][objects]
- `CZSC` 只维护 `bars_raw`、`bars_ubi`、`bi_list`，没有 `xd_list`。
  [分析器状态][analyze-czsc]
- 绘图函数虽然接受 `xd=[{"dt": ..., "xd": ...}]`，但只负责把外部输入连成线，
  不负责计算线段。[ECharts 线段输入][echarts]

所以本项目设计中的“特征序列 -> 标准特征序列 -> 缺口或分型破坏 -> 线段中枢”
仍需自行实现。0.9 不能作为该部分的现成组件。

### 4. 多周期与信号

`BarGenerator` 接收一个基础周期，按市场交易时段持续合成多个更高周期；同一高级别
周期尚未结束时，会更新该周期最后一根 K 线。[多周期合成源码][bar-generator]

`CzscSignals` 为每个周期维护一个 `CZSC` 实例。收到基础周期 K 线后，它先更新
`BarGenerator`，再更新每个周期的分析器，最后按 `signals_config` 动态调用信号
函数。[多周期信号编排][traders-base]

0.9 的信号约定具有两个值得参考的点：

1. 函数名带版本日期，例如 `cxt_third_bs_V230319`，旧口径可以与新口径并存。
2. 信号配置声明函数名、周期和参数，多周期函数既可接收单周期 `CZSC`，也可接收
   整个 `CzscSignals`。

但它的输出把信号编码为下划线分隔字符串，`Signal -> Factor -> Event -> Position`
再解析字符串执行交易。[信号与事件对象][objects-signals] 这种协议不适合本项目的
事实引用、结构化校验和报告冻结，不能直接搬入生产契约。

### 5. 背驰与买卖点

0.9 提供大量“辅助信号”，但不存在唯一、统一的一二三类买卖点事实链：

- `cxt_first_buy_V221126` 用笔的价差、成交量和长度比较判断背驰，不是本项目设计的
  线段中枢与 MACD 趋势背驰。[一买源码][cxt-first-buy]
- `zdy_macd_bc_V230422` 在调用方截取的 5、7、9 笔窗口中构造 `ZS`，比较进入笔和
  离开笔的 MACD 面积、DIF 和价格极值。[MACD 背驰源码][zdy-macd-bc]
- `cxt_third_bs_V230319` 用 1、2、3 笔重叠、4 笔离开、5 笔回抽不进入中枢，再加
  均线形态判断三买三卖。[三买三卖源码][cxt-third-bs]
- `cxt_zhong_shu_gong_zhen_V221221` 同时读取大小周期最近三笔中枢，根据相对位置和
  小周期末笔方向输出看多或看空。[中枢共振源码][cxt-resonance]

这些函数适合用来建立候选规则和差分样本，不适合直接成为本项目的报告事实源。
本项目仍应坚持“结构形成 -> 趋势或盘整 -> 背驰证据 -> 次级别确认 -> 结构化信号”
的单一链路。

还要特别注意 MACD 参数口径：0.9 的通用实现默认是快 12、慢 26、信号 9，
但 `zdy_macd_bc_V230422` 显式传入快 26、慢 12、信号 9，和本项目设计固定的
12/26/9 相反。[MACD 通用实现][ta-macd] [背驰调用参数][zdy-macd-bc]
因此只能参考面积比较思路，不能直接复制该函数结果或阈值。

### 6. 可视化

`kline_pro` 基于 pyecharts，也就是服务端生成 ECharts 配置和完整 HTML。它已经
包含 K 线、均线、分型、笔、外部线段、成交量、MACD 和买卖点图层。
[pyecharts 绘图源码][echarts]

但它没有中枢参数，也没有 `markArea` 或矩形中枢图层。`CZSC.to_echarts` 只把
K 线、分型和笔传给绘图函数。[CZSC 绘图入口][analyze-chart]

因此：

- 可以参考其分型散点、MACD 第三网格、买卖点图标和线段折线样式。
- 不要把 pyecharts HTML 或 Python `lightweight_charts.Chart` 嵌入当前 React 页面。
- 当前前端的 ECharts `markArea` 中枢绘制已经优于 CZSC 0.9，应继续保留。

## 能力对照与复用边界

| 能力 | 本项目现状 | CZSC 0.9 帮助 | 结论 |
| --- | --- | --- | --- |
| 包含、分型、笔 | 已有轻量实现 | 有成熟尾部更新和来源对象 | 差分后选择性改造 |
| 笔中枢 | 已有顺序中枢 | 有中枢派生属性和有效性检查 | 可移植属性，不替换分组 |
| 线段 | 仅有设计 | 没有核心模型，绘图只接外部 `xd` | 继续自行实现 |
| MACD 背驰 | 仅有设计 | 有多种窗口型辅助信号 | 规则候选和测试参考 |
| 一二三类买卖点 | 仅有设计 | 多套不统一的辅助口径 | 不直接作为事实源 |
| 多周期确认 | 日、周已接入，30 分钟待建 | 合成与统一编排成熟 | 重点借鉴职责边界 |
| 重放性能 | `replay` 当前反复全量规约 | CZSC 只重算末端 | 优先优化，但保持等价性 |
| 数据追溯 | 有时间可用性和冻结快照 | 没有对应契约 | 必须保留本项目实现 |
| 图表 | React + ECharts，已有中枢 | 有分型、MACD、信号样式 | 只移植图层设计 |
| 交易执行 | 尚未建设 | `Factor/Event/Position` 很完整 | 当前不要引入 |

## 三类结合建议

### 可直接移植

这里的“直接”指局部纯逻辑能映射到现有类型，不表示复制整个模块。

1. 在现有 `Center` 结果上补充 `gg`、`dd`、`zz` 和 `is_valid` 派生计算，价格继续
   使用 `Decimal`，不改变当前中枢分组规则。
2. 把 CZSC 官方 `test/data/000001.SH_D.csv`、`test_analyze.py`、
   `test_objects.py` 中的结构不变量转成离线差分用例；如复制官方数据或代码，保留
   Apache-2.0 许可说明。[官方分析测试][test-analyze]
3. 在当前 `buildChanChartOption` 中增加分型散点、MACD 网格、线段折线和买卖点散点
   时，直接沿用 CZSC 的图层职责划分，但使用当前 TypeScript 数据类型。

### 需要改造后引入

1. **尾部增量状态**：借鉴 `bars_ubi + bi_list + 回退最后一笔`，但内部状态必须以
   `Decimal` 和来源索引表示；同时间冲突仍按本项目规则拒绝。
2. **结构对象分层**：可以新增内部 `NormalizedBar`、`Fractal`、`Stroke`、
   `Center` 数据类，但外部 snapshot 旧键只增不改，并保留三个时间字段。
3. **信号注册**：借鉴版本化函数和配置驱动调用，输出改成结构化 `Signal`，禁止
   下划线字符串协议和动态任意导入。
4. **多周期编排**：借鉴“一份基础输入、每周期一个引擎、信号声明周期依赖”，但
   30 分钟行情仍应预拉入库；分析链只读缓存，不在请求时实时合成或补拉。
5. **少量信号规则**：只选择与需求一致的 MACD 趋势背驰、二类回抽、三类不回中枢
   几何条件。CZSC 结果只作旁路参考，最终状态由本项目规则和次级别确认决定。

### 不要引入

1. 不安装完整 `czsc==0.9.68` 作为生产依赖。
2. 不引入 `rs_czsc`、TA-Lib、Streamlit、pyecharts、Redis、OSS 等整套依赖。
3. 不用 `RawBar.cache` 这种任意可变字典保存报告事实。
4. 不接受同时间 K 线静默覆盖，避免历史报告不可复现。
5. 不复制 259 个信号函数，也不使用 `Signal/Factor/Event` 字符串协议。
6. 不引入 CZSC 的 `Position`、回测、行情连接器和服务层；它们超出当前请求。
7. 不用后端生成的 HTML 图替换当前 React/ECharts 图表。

## 推荐目标架构

```text
                    仅测试 / 研究环境
固化行情夹具 ---------> CZSC 0.9 对照器
      |                      |
      |                  结构差分报告
      v                      |
CanonicalBar ---------------+
      |
      v
ChanEngine
  normalize -> fractals -> strokes -> centers
                    -> segments -> MACD -> typed signals
      |
      +-> snapshot + known_at / stable_through + engine_version
      |
      v
MultiTimeframeCoordinator
  1w / 1d / 30m 只读固化缓存，执行次级别确认

      v
```

CZSC 只存在于左侧旁路和设计参考中。生产链只有一个权威结构快照，避免出现
“CZSC 算法结果”和“本项目算法结果”同时进入报告的双事实源。

## 最小增量路线

### 第一步：建立 0.9 差分基线

不改生产依赖，先选择 3 至 5 组固化前复权 K 线，覆盖：

- 连续包含和方向切换。
- 连续同类分型取极值。
- 最后一笔被后续 K 线破坏。
- 单中枢延伸、离开后新中枢。
- 跳空和同时间冲突。

在独立测试适配器中完成以下字段映射：

| 本项目 | CZSC 0.9 对照输入 |
| --- | --- |
| `occurred_at` | `dt` |
| 输入顺序索引 | `id` |
| `Decimal` OHLC | 仅在对照器边界转换为 `float` |
| `volume` | `vol` |
| `known_at/stable_through/payload_hash` | 不进入 CZSC，只用于本项目断言 |

差分结果分为“实现缺陷、规则口径差异、浮点差异”三类，不把完全相等作为唯一通过
条件。

### 第二步：先优化重放，再增加新能力

当前 `replay` 逐根调用 `ingest`，而 `ingest` 每次线性检查重复并全量 `_reduce`，
静态复杂度接近二次方。30 分钟五年数据会放大这个问题。

建议顺序：

1. 按已有信号栈设计移除 `_frozen_confirmed` 的按数量拼接。
2. `replay` 一次完成输入转换、唯一性和顺序校验，再只调用一次 `_reduce`。
3. 用哈希索引把 `ingest` 的重复检查从线性扫描改为常数时间查询。
4. 以“批量 replay 等于逐根 ingest”为硬回归门禁。
5. 性能仍不够时，再借鉴 CZSC 的尾部增量状态；不要在第一步就引入复杂可变状态。

这一步能直接为未来约万根 30 分钟 K 线回放降本，优先级高于接入更多信号。

### 第三步：补结构来源和中枢派生属性

在内部对象记录归一化 K 线的原始来源索引、分型三根 K 线索引、笔内部范围。外部
snapshot 继续使用稳定字典，只追加确实需要的字段。随后把 `gg`、`dd`、`zz` 和
有效性检查作为纯函数加入中枢层。

这一步借鉴 CZSC 的对象分层，但不引入它的可变 `cache`，也不改变现有中枢划分。

### 第四步：实现本项目自己的线段和三类信号

线段仍按本项目设计的特征序列规则实现。CZSC 0.9 只提供笔级辅助样本：

1. MACD 使用本地纯函数并输出与结构 K 线对齐的快照数组。
2. 一类只来自本项目定义的趋势背驰，并要求次级别确认。
3. 二类使用一类后的首次有效回抽规则。
4. 三类借鉴“中枢离开后回抽不进入”的几何条件，但使用本项目线段中枢。
5. 每个信号输出价格、时间、来源结构索引、确认状态和固定原因枚举。

### 第五步：扩展现有 ECharts，不增加第二套图表运行时

在 `ChanChartData` 中只追加：

- `fractals`
- `segments`
- `macd`
- `signals`

保留现有 K 线、笔、中枢和成交量字段。图表新增分型散点、线段折线、MACD 子图和
买卖点散点；中枢继续使用现有 `markArea`。不要嵌入 CZSC 生成的 HTML。

## 第一批最值得实施的改动

如果只做一个最小迭代，建议范围固定为：

1. 建立 CZSC 0.9 差分夹具与结果分类。
2. 修复 `replay` 的二次方路径，并删除冻结前缀拼接。
3. 为当前中枢补 `gg`、`dd`、`zz` 派生值。
4. 前端只新增分型散点，不在同一迭代引入 MACD、线段和买卖点。

这四项能同时提高正确性、性能、可解释性和可视化核验效率，又不会提前改变报告的
买卖点语义。后续再按“线段 -> MACD -> 背驰 -> 次级别确认 -> 图表标记”逐层推进。

## 最终判断

CZSC 0.9 最适合成为本项目的“算法参考库和差分 Oracle”，不是生产运行时。

应当吸收的是末端增量状态、结构来源、多周期职责划分、版本化信号和图层设计；
必须保留的是本项目的 `Decimal`、时间可用性、输入冲突、快照冻结、结构化信号和
React/ECharts 契约；仍需自行建设的是线段、线段中枢、严格走势类型和次级别确认。
